# AI Agent 助手：Function Calling + RAG 知识库问答

一个用**纯 Python（无框架依赖）**实现的 AI Agent，支持工具调用、知识库检索、流式输出和多轮对话，并封装为 HTTP 接口供外部调用。

> 本项目为转型 AI 应用开发期间的学习产出，所有核心环节（切片、检索、工具路由、流式解析）均手写实现，未使用 LangChain / LlamaIndex 等框架，目的是理解 RAG 与 Agent 的底层机制。

---

## 功能特性

- **工具调用（Function Calling）**：4 个工具自主路由，模型根据问题自己决定调哪个
- **RAG 知识库问答**：文档按语义边界切片 → 向量化 → 余弦相似度召回 → 拼接提示词
- **反幻觉约束**：资料中没有的内容，明确回答“资料中没有提到”，不编造
- **流式输出**：SSE 流式解析，终端打字机效果
- **多轮记忆**：维护 messages 历史，支持上下文追问
- **HTTP 服务**：FastAPI 封装，自动生成交互式接口文档
- **向量持久化**：建库结果缓存到本地文件，mtime 校验，文档没变则启动秒开
- **请求日志**：记录每个请求的问题与耗时，便于定位慢请求
- **异步处理**：`httpx.AsyncClient` 并发处理，等待模型返回时不阻塞其他请求

## 架构

```
                        ┌─────────────────┐
   用户提问  ──────────▶ │   DeepSeek API  │
                        │  (决定是否调工具) │
                        └────────┬────────┘
                                 │ tool_calls
                    ┌────────────▼────────────┐
                    │      TOOL_MAP 分发       │
                    └──┬──────┬──────┬──────┬──┘
                       │      │      │      │
                 get_time  get_date  get_weather  search_kb
                                                    │
                                        ┌───────────▼───────────┐
                                        │  向量检索（RAG）       │
                                        │  embedding → 余弦排序  │
                                        └───────────┬───────────┘
                                                    │
                                            kb_reimburse.md
```

**关键设计**：RAG 不是一个固定流程，而是**包装成工具**交给模型调度。问“今天几号”不会去查知识库，问“住宿标准”才会。

## 快速开始

### 1. 安装依赖

```bash
pip install requests python-dotenv fastapi uvicorn
```

### 2. 配置密钥

在项目根目录创建 `.env`：

```
DEEPSEEK_API_KEY=sk-xxx          # https://platform.deepseek.com
ZHIPU_API_KEY=xxx                # https://open.bigmodel.cn（用于 embedding）
```

### 3a. 终端交互模式

```bash
python chat_rag.py
```

### 3b. HTTP 服务模式

```bash
python -m uvicorn api_server:app --reload --port 8000
```

浏览器打开 <http://127.0.0.1:8000/docs> 可直接在页面上调用接口。

## 接口说明

### `POST /chat`

请求：

```json
{ "question": "住店能报多少" }
```

响应：

```json
{
  "question": "住店能报多少",
  "answer": "一线城市每晚不超过 600 元；二线城市 450 元；其他城市 350 元……"
}
```

## 设计说明

### 为什么按段落切片，而不是固定字数

固定 200 字硬切会把标题和内容劈开：`## 三、住宿费标准` 落在上一块，`600/450/350` 落在下一块。两边都不完整，检索时“住宿费标准”这一块字面命中为 0。

实测对比（同一文档、同一检索算法）：

| 切片方式 | 正确答案所在块的得分 |
|---|---|
| 每 200 字硬切 | 0 分（排在最后） |
| 按段落切 | 4 分（排第一） |

**切片质量直接决定检索质量**——这是 RAG 中最容易被忽视、也最先出问题的一环。

### 为什么用向量而不是关键词

关键词检索（中文 2 字滑窗）对同义改写完全失效：

- 用户问「住店能报多少钱」
- 文档写「住宿费标准」

两者字面几乎零重合，关键词检索召回错误。改用 embedding（2048 维）+ 余弦相似度后准确召回。

实测相似度：

| 对比 | 余弦值 |
|---|---|
| 住宿费标准 vs 住店能报多少钱 | **0.763** |
| 住宿费标准 vs 今天天气怎么样 | 0.444 |

### 为什么 RAG 要做成工具

写死流程（每句话都先检索）会导致问“今天几号”也去翻制度文档，既浪费又容易答偏。包成工具后，由模型自己判断，这才是 Agent 与固定流水线的区别。

### 为什么接口用非流式

流式是给人眼看的（打字机效果），接口返回值是给程序读的。程序需要一个完整的 JSON，碎片反而增加对接成本。

**人看用流式，机读用完整。**

### 为什么要缓存和异步

**缓存**：建库（embedding）是重活——8 块约 3 秒，1 万份文档要几小时，而且按 token 计费。用文件修改时间（mtime）当指纹：文档没变就直接读缓存，变了才重建。启动从「算一遍」变成「读文件」。

**异步**：模型调用是网络 I/O，一次 3~5 秒里 CPU 几乎不干活。同步写法下一个请求占一个线程，几十人同时问就排队。改用 `httpx.AsyncClient` 后，等待期间可以处理别的请求——实测两个并发请求各约 3 秒完成，而非串行的 6 秒。

⚠️ 关键约束：**异步函数里不能调同步阻塞库**（如 `requests`），否则会堵死整个事件循环，比不改造更糟。

## 踩坑记录

| 问题 | 原因 | 结论 |
|---|---|---|
| 知识库建库 0 块，检索永远返回“没找到” | `f.read()` 被调用了两次，第二次读到空字符串，且**不报错** | 静默失败比报错危险；关键数据要打印校验 |
| 智谱 embed 报 `1210 参数有误` | 8 个完整章节一次批量提交，超出单次长度限制 | 改逐条请求，失败时打印出错块 |
| 向量版检索恒返回“没找到” | 沿用了字面版的判断 `score == 0`，而余弦值永远不会是 0 | 换了算法，判断口径也要跟着换 |
| `KeyError: 'data'` | 直接硬取响应字段，真实错误信息被吞掉 | 先取 `r.json()`，判空后再取字段 |

## 已知限制

- 知识库为单文件加载，修改文档需重启（mtime 变化会自动重建缓存）
- 向量缓存用 JSON 存储，万级文档需换 `.npy` 或向量数据库
- 检索未加重排序，长文档场景召回精度有限
- 会话状态未外置，多实例部署会各自失忆（需 Redis）
- 未做鉴权与限流，仅供本地学习使用
